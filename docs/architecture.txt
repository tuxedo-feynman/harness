Effect Actions: 
- tool plugins that effect the outside world, text messages, calendars, timers, chats, home automation, etc... 

Thinking Actions:
- AI API's that can make decisions given context, request, and an ActionDirectory on what to do context

Null Action:
- Terminating Action: ends the current branch. Policy Controller requests it when a branch is genuinely over (e.g. a channel quit). Turns normally end by returning to listening, not by Null.

Listeners:
- Every listening channel (terminal, telegram, ...) holds exactly one live pending Operand: an unresolved input request -- a request for the channel's next event (message, poll vote, ...). It resolves with an ActionResult when the world produces one.
- When a turn completes, the other channels' pending input requests are MOVED (reparented, same operand -- it is the same subscription) to the new tip as siblings of the fresh one, so any channel's next event continues from the full conversation. One shared history across all channels.


Execution Loop:
- Anchored on a resolved stimulus operand. Each cycle: Build Context from the frontier (the resolved operands whose results feed the next decision) --> Policy Controller decides and creates the child operands --> execute them sequentially in sibling order --> the children become the next frontier. [[REPEAT until an input request parks or a Null Action executes]]
- Single-threaded: children execute in sibling order; each child's result resolves that child.
- Requests whose method is named input are PARKED (left unresolved, registered as that channel's pending listener) instead of executed.

Dispatcher:
- The stimulus boundary. One thread per listening channel blocks on the channel and pushes results onto a queue; threads know nothing about operands.
- The single-threaded dispatch loop resolves each stimulus against that channel's pending listener operand (attribution at dequeue time), then runs the execution loop from it. All operand mutation happens on this thread.


Operand:
- Primary internal data model: one node of the operand DAG. A single request for an event, resolved when that event arrives (a thinking request by a completion, a send by its delivery, an input request by the channel's next event). One rule, no special casing: an operand's parents are exactly the operands whose results its request consumes -- a chain is the one-parent case; a thinking operand that read three tool results has all three as parents.
{
    id: uuid
    created_at: datetime
    parents: [uuid]
    order: int  // position among siblings; deliberately sibling-local (a global sequence would conflate with id and overflow a years-long agent life)
    action_request: ActionDescription | None  // None only on the synthetic root
    action_result: ActionResult | None  // None while the request is a pending promise
}

Context:
- Internal representation handed to Policy Controller and Thinking Actions
{
    system_prompt: str
    history: [Operand]  // the ancestor closure of the frontier, linearized: topological order with sibling-order tie-breaks -- deterministic
    available_actions: dict[str, {kind, methods: dict[str, MethodDescription]}]  // action_name -> kind + method_name -> MethodDescription. kind is included so Thinking Actions can filter what they advertise as callable (e.g. effect-only), while still allowing policy-sanctioned thinking-calls-thinking setups.
    listeners: [Operand]  // live pending input operands -- off the ancestor closure, so only visible here
}

Context Builder:
- Owns the operand DAG for the life of the process. The graph (parent pointers) is the sole source of truth; the flat storage list is an implementation detail.
- An explicit synthetic root operand starts the graph; the initial input requests attach as its children.
- Invariants: children only attach beneath resolved operands, so unresolved operands are always leaves. Resolved operands are immutable history; unresolved operands are live state -- moved by Context Builder.
- move() reparents a pending operand (the prune-and-move of uncle listeners). Only unresolved operands may move.
- build(frontier) renders the context as seen from the frontier: history is the ancestor closure, linearized in topological order with sibling-order tie-breaks, so pending listeners and dead branches are excluded automatically and rendering is deterministic. available_actions is a read-only projection of Action.methods per registered Action -- never the ActionDirectory itself, so Actions can't call other Actions directly and bypass Policy Controller.

  Policy Controller:
  - A bunch of conditional logic, inspects the resolved frontier and decides whether to short-circuit a thinking action and go directly to null or effect action.
  - Primary path: creates the child operands for the next cycle (parents = the frontier, order = position in the batch), each carrying one ActionDescription.
  - Owns the end-of-turn listening decision: which channels keep a pending input request (quit = omit that channel's), where responses are delivered (the origin channel of the current branch), and when the uncle listeners move to the tip (mechanics executed by Context Builder).
  - Logs every decision it makes: requests attached, requests vetoed or modified, short-circuits taken.


  Action Directory:
  - a map of name --> Action
  - method_index() returns a map of action_name --> method_name --> MethodDescription, used by Context Builder to populate Context.available_actions
  - descriptions() returns a string of the descriptions of all Actions and their functionality, as well as how to call them -- for logging/debugging, not used to populate Context

Action:
- Base class for tools and API's to implement, think telegram, ChatGPT, terminal, etc...
  (
      name: str
      kind: ['thinking, effect', 'null']
      description: str
      methods: dict[str, MethodDescription]

      def run(method_name: str, arguments: dict[str, any], context: Context) -> ActionResult

  MethodDescription(
    name: str
    description: str
    parameters_schema: dict[str, Any]
  )

- Canonical method names are hyh's verb vocabulary -- the name IS the marker, there are no flags. Channel actions expose "input" (a request for the channel's next event -- message, poll vote, ...; parks as a pending operand until the world resolves it) and "send" (tell the world); thinking actions expose "complete". Each action translates the verb into its underlying call (input(), getUpdates, chat.completions.create, ...). At most one input method per action holds by construction.
)



ActionDescription:
- Data model created so that an Action can be called
{
  id: uuid
  action_name: str
  method_name: str
  method_parameters: dict[str, Any]
}

ActionResult:
- The result of an Action
{
    contents: str
    metadata: dict[str, Any]  // structured event data from the world (e.g. the telegram chat_id a message came from). Requests record intent; results record events. Policy draws delivery addressing from the origin stimulus's metadata.
    action_description_requests: [ActionDescription]
    error: str | None
  }
